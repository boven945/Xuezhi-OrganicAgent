## 3. 实施过程中被实测推翻的判断

这一节是本文的核心。**以下每一条我都曾"以为"是对的，
实测证明是错的。**记录下来是为了避免重复。

### 3.1 RDKit API：`Mol.GetSmarts()` 不存在

写化学引擎时我"记得"RDKit 有这个方法，用于还原 SMARTS 文本。
真实调用报 `AttributeError`，`dir()` 查无此法——**是我凭印象编的**。

修正：改为保留 `_FUNCTIONAL_GROUPS` 表中的原始 SMARTS 文本，
编译结果改为 `(名, 原文, Mol)` 三元组。

首轮测试 28 项失败，4 项同源于此类凭记忆假设。

### 3.2 RDKit 行为：三个"常识"其实错了

| 我的假设 | 实测事实 |
|---|---|
| 单个 `"C"` 是非法 SMILES | **合法**——是甲基自由基，formula=CH₄ |
| `CC#N` 可用于测碳碳三键 | **是氰基**（C≡N），不含碳碳三键；须用乙炔 `C#C` |
| 乙醇 `GetNumAtoms()` 是 9 | **是 3**——该方法返回显式原子数，不含隐式氢 |

第三条已在 `models.py` 的字段注释中写明语义，避免使用者误解。

### 3.3 LangChain：与 OpenAI 原始 SDK 结构完全不同

这是影响最大的一次。按 OpenAI 规范写了 dispatcher，
真实调用**全部失败**：

| | OpenAI 原始 SDK | **LangChain `bind_tools`（实测）** |
| --- | --- | --- |
| 返回值 | 响应对象含 `choices[0].message` | **`AIMessage`，没有 `choices`** |
| tool_call 元素 | 对象 `call.function.name` | **dict `{"name","args","id","type"}`** |
| `args` 类型 | **JSON 字符串** | **已解析的 dict** |
| assistant 回填 | 需手工构造 dict | **`AIMessage` 可原样回传** |

三个假设全错：按规范写的 `response.choices[0].message`、
`call.function.name`、`json.loads(arguments)`。

已记入决策登记表 A1-note，并确立规则：**写 LangChain 代码前先
真实调用一次并 dump 结构**。

### 3.4 sentence-transformers：API 改名且不报错

`get_sentence_embedding_dimension` 已改名 `get_embedding_dimension`。
旧名**仍然可用，只发 `FutureWarning`**——测试显示"全部通过"。

只有开 `-W error::FutureWarning` 才暴露。**若只看测试通过就放过，
这个过时 API 会潜伏到未来版本移除才炸。**

已改为新名 + `getattr` 兼容旧版，并确立规则：
**跑依赖库测试时加 `-W error::FutureWarning`**。

### 3.5 chromadb：内置 embedding 是英文模型，中文排序完全颠倒

查证 chromadb 1.5.9 内置 `DefaultEmbeddingFunction`，
实测 cosine 空间查「酯化反应」：

| 文档 | 距离 | 实际名次 |
| --- | --- | --- |
| 酯化反应是酸和醇生成酯和水 | **0.8358** | 第 3 ❌（应该第 1） |
| 今天天气很好 | **0.4943** | 第 1 ❌（应该第 3） |

**排序完全颠倒。** 换英文 query 后排序正确，确认为模型语言问题。
这一条直接催生了 H17 阻塞项，并促成改用 `BAAI/bge-small-zh`。

同批查证还发现：默认距离度量是 `l2` 非余弦；内置 EF 首次调用需
联网下载 79.3MB ONNX 模型（断网演示会失败）。

### 3.6 openPangu 协议：tool_choice 不支持指定具体函数

传 OpenAI 规范的 `{"type":"function","function":{"name":...}}` 报
`ModelArts.81001: The Pangu model supports only "none", "auto", and "required"`。

**这是与 OpenAI 规范的差异**，无法强制指定某函数。
工具收敛只能靠白名单 + 提示词引导——反而让
`architecture.md` §5 的白名单机制显得更必要。

另一发现：模型**默认开启深度思考**，返回 message 含
`reasoning_content`。设 `max_completion_tokens=200` 会导致
正文完全为空（token 被思考占用）——这曾让我一度误判为 API 故障。

### 3.7 切分策略：语义切分实测更差

联网核实（详见 `knowledge-base-implementation.md` §3）：
FloTorch 2026 基准（50 篇论文、90 万 token）端到端准确率——
递归字符切分 512 token = **69%**，固定大小 = 67%，
**语义切分仅 54%**（产出 43 token 碎片，检索中但答不出）。

**我原本倾向语义切分**（听起来更先进），实测数据推翻了这一倾向。

### 3.8 教材版权：把他人作品用于 AI 知识库不构成合理使用

联网核实到的明确立场：台湾高校图书馆与经济部知识产权局均指出
未经授权将电子书用于知识库建置超出合理使用范围。

**这直接改变了方案**：从"引入教材"改为"自编讲义"。
详见 `organic-corpus-verification.md` §2。

## 4. 本机环境的两个硬约束

### 4.1 Smart App Control 拦截未签名二进制

Windows Smart App Control 已启用，按**发布者签名**拦截二进制：

| 扩展 | 签名 | 加载 |
| --- | --- | --- |
| numpy / scipy / Pillow | 有 Microsoft 签名 | ✅ |
| **rdkit / grpcio** | **NotSigned** | ❌ 被拦 |

事件日志 3077 给出确切原因：RDKitSubstructMatch-*.dll
不满足 Enterprise signing level。

**关键结论：能否加载原生扩展取决于 Python 的**发行来源**，不是版本。**
同为 3.12.14：uv 发行版可用，conda-forge 环境连标准库 `_ctypes` 都被拦。

依次尝试了三条绕行路径（conda 环境、Docker、关闭 SAC），
前两条失败（详见 `chem-engine-verification.md` §2.3），
**最终由用户完成 Docker Desktop 的 WSL2 后端初始化解决**——
容器内二进制不受主机策略管辖。

**处置原则：没有关闭 Smart App Control，也没有为绕过策略在产品代码
里加任何 hack。** 由项目负责人指定测试环境是正确的做法。

### 4.2 网络：直连 30 kB/s，必须走代理

同一下载目标实测：直连 28.7 kB/s，代理 `127.0.0.1:7897` 达 1.02 MB/s，
**相差 35 倍**。直连条件下完整安装 30 分钟未完成，走代理 4 分钟完成。

依赖安装须显式加 `--proxy http://127.0.0.1:7897`。
HuggingFace 直连不通（HTTP 000），bge 权重须代理下载。

## 6. 一个工程纪律上的问题（需要正视）

**分支纪律没有真正发挥作用。**

本项目规范要求「一个模块一个分支」，但实测结果是：
8 个功能分支最终形成了**单一线性链**，14 个提交全在最后一个分支上。
验证数据：

```
feat/backend-chem-rdkit-engine           +4
feat/backend-llm-model-adapter          +7   （在其上继续）
feat/backend-agent-tool-dispatcher      +8   （在其上继续）
...
feat/knowledge-organic-chemistry-corpus +14  （最终分支）
```

**原因分析**：每个模块都在前一个模块的分支上继续开发，
`git checkout -b` 时新分支包含了旧分支的全部历史。
这在实践中是**低效但不有害**的——它保证了每个提交都是可运行的，
但也意味着：

- 无法单独检出某个模块的分支
- 无法对单个模块做 code review 或 cherry-pick
- 分支名暗示的"模块隔离"与实际内容不符

**改进方向**（待定）：后续若并行开发多个模块，
应从 `main` 切分支而非从当前分支切，合并时用
`--no-ff` 保留分支拓扑，让模块边界在历史上可见。

本文记录这一事实而非掩盖，因为**留痕的价值包括记录做错的地方**。

## 10. 第二轮：把"记下来"变成"自动化检查"

§9 记了 4 项失误。其中**第 1 项（改决策表导致行首丢空格）在同一天又犯了一次**。

### 同一个错误犯两次，说明记进文档不够

- 第一次（约15:00）：自写 `'| ' + ' | '.join(cells)` 导致行首多空格；
- 第二次（约 18:00）：修好之后另开分支改 I2/I3，
  又用 `'|'+'|'.join(cells)+'|'` 拼行——把 `| ` 变成 `||`。

两次都让 `grep "^| I2 |"` 匹配不到，症状完全一样：
**"决策项不见了"**。

**结论：靠自觉执行规则是不可靠的，须把规则固化成检查。**
已新增 `backend/tests/knowledge/test_docs_format.py`（83 项），
覆盖行首 `||`、乱码、编号重复、列数一致、死链、索引完整。

### 又踩了一次"镜像里没有该文件"

新增文档测试后立刻 `FileNotFoundError`——
`Dockerfile.test` 只 `COPY backend/` 与 `data/`，**`docs/` 不在镜像里**。

这与§9 第 2 项同源：**镜像用 COPY 烘入源码，

## 11. 第三轮：前端模块（4 项失误，其中 1 项差点让验证失效）

### ① 依赖版本是凭印象写的（最典型的错误）

`@vue/test-utils` 写了 `2.4.6`、`happy-dom` 写了 `20.0.11`——
`npm view` 一查，实际 latest 分别是 **2.5.1** 与 **20.14.5**。

**这与本项目之前记录的"凭印象断言 SMARTS 不存在"是同一类错误。**
凭印象写版本号之所以难自查，是因为**装得上、跑得起**，
只是版本偏旧几个月，不影响功能——直到某天上游发一个
补丁版本引入破坏性变更，才发现当初锁的是个不存在的组合。

**规则**：任何写入 `package.json` 的版本号必须来自
`npm view <pkg> version` 的实测输出。

### ② E2E 的流式断言形同虚设（差点让验证结论失效）

第一版E2E 只断言「流式过程中已有部分文本」。结果
`03-streaming.png` 与 `04-answer-done.png` **字节完全相同**——
等待时间过长，抓到的其实是完成态。

**这与之前"写了 E2E 却没重建镜像就宣布全量通过"是同一类错误**：
验证代码本身有缺陷，测试通过不代表验证了目标行为。

改为断言**中途长度 < 最终长度**（7字 < 37 字）才真正测到流式。
并把后端探针放慢到 60ms/字（约 2.2 秒）让中间态可观察。

**教训**：验证流式/异步行为时，断言必须能区分
「与目标行为一致」和「与错误行为一致」。若二者产生相同观测，
断言就是无效的。

### ③ `unknown` 是死分支（我自己的注释与代码矛盾）

`toSourceItem` 里写了 `else if (locator) kind = 'section'`，
而注释说"推断失败一律回落 `unknown`"。这两句**互相矛盾**——
非空的 `locator` 永远命中 `section`，`unknown` 走不到。

测试用例 `无法推断时回落 unknown，不猜` 抓出。

**这类"注释说一套、代码做一套"的问题最难靠读代码发现**，
因为读的时候两边都在眼前。只有断言能发现。

### ④ 改决策表时又写出行首 `||`（同一天第 4 次）

新写的 I6 条目里嵌了裸 `\n`，把一个表格行拆成三行；
加上自写`'|'+'|'.join(...)` 拼接，产生了 `||A2 |`。

**新建的 `test_docs_format.py` 立刻抓到**，
一次报出 4 个问题（行首 `||`、列数超限、状态列错位、文档未挂载）——
**这正是当初把规则机械化的价值**。前三次靠自觉都漏了，
第四次靠检查一次全中。

**附带修正方式**：脚本插入含 `\n` 的文本时，
应写成一个逻辑行再拼接，否则会破坏表格结构。

### ⑤ 顺带修掉一个真实的依赖卫生问题

`vue-router` 最初写入 `package.json` 但代码里没用它。
本项目规则是**不装不用的东西**——留着会让 `npm audit`
报出与项目无关的漏洞噪声，掩盖真实问题。已移除。

## 容器化运行 RDKit 与错误文案补齐（2026-10-04 晚）

### 背景

用户提供了外部排查文档，建议「把 RDKit 做成独立容器服务，主机跑FastAPI，
主机通过 `localhost:8001` 调容器」。要求**不要全信，大量联网搜索**。

### 一、被推翻的判断：我上一轮说错了一处

我此前说「Docker 需要安装」。实测本机**已经装好且可用**：


核实来源：WDAC / AppLocker 管辖 **Windows PE 可执行文件**，
对 WSL2 内的 **Linux ELF 不生效**（官方与企业实践文档均确认），
故 Docker Desktop 的 WSL2 后端天然不受该策略管辖。

### 二、外部方案的三处冲突（不照抄）

| 外部方案 | 本项目实际情况 | 判定 |
| --- | --- | --- |
| `apt install libboost-all-dev` | pip wheel 自带全部 `.so`/`.dll`，不需要 boost；既有测试镜像未装即正常 | 白装数百 MB |
| `FROM python:3.11-slim` | 基线是 3.12（H1），回退会重新引入 numpy/pandas 版本压制 | 基线倒退 |
| `pip install rdkit>=2024.03.2` | 须锁定，既有镜像锁 `rdkit==2026.3.6` 且容器内实测可用 | 违反 E4 |

### 三、未采纳「拆成独立化学服务」的理由

`chem/engine.py` 456 行承担 12 条官能团 SMARTS、性质计算、原子/键表、
ETKDG 坐标、输入限长与受控错误码。改为跨进程 HTTP 调用需新增
序列化协议、网络失败模式、错误码往返映射——**为绕开 DLL 拦截反而扩大失败面**。

改为**容器跑完整后端**后实测`/health` 报 `chem: ready=true`，
`chem/engine.py` 零改动，前端 `VITE_BACKEND_URL` 机制已存在。

### 四、本机shell 陷阱（差点误判成缺依赖）

首次在容器内起服务失败，报 `ModuleNotFoundError: No module named 'app'`。
真实原因不是缺依赖，而是 **Git Bash 把 `/work/backend` 展平成Windows 路径**：

```text
PYTHONPATH=C:/Users/Lenovo/.workbuddy/binaries/PortableGit/versions/1.2.0/work/backend
```

加 `MSYS_NO_PATHCONV=1` 后正常。**这个现象极易被误判为镜像缺包**——
我第一次也确实先怀疑是依赖问题，查了 `sys.path` 才发现。

### 五、顺带发现一个真实缺陷：错误文案全落通用兜底

容器内逐接口验证时发现，学生输入非法结构式（`C1CC`）得到的是
**「服务暂时不可用，请稍后重试」**——但服务一切正常，
错的只是少写一个右括号。**误导性文案比报错更糟**：
它暗示重试就能好，学生会反复重试而不去检查输入。

根因：`DOMAIN_MESSAGES` **整段没有 chem**。
补齐后我加了**反向一致性检查**（原先只查孤儿码、不查缺失），
它立刻又查出 12 个缺失码/未登记状态码，包括
`rag_invalid_document` 漏登记会落到保守默认 **500**。

**教训**：一致性检查必须**双向**。孤儿码（写了没用的文案）有害但冗余，
缺失码（学生拿到误导提示）有害，而后者恰好是原测试的盲区——
几百个测试全绿而缺陷存在。

### 六、修正了一个历史测试的失效前提

`test_public_message_hides_domain_message` 原用
`InvalidStructureError` 当「未登记码」的反例，依赖「chem 未登记」。
chem 补齐后该前提失效（本层文案也含「括号」二字），
改用 `ToolTimeoutError`。该用例验证的是**机制**（不透传异常自带文案），
不该被文案表内容变化牵连。

### 七、失误与代价

| 失误 | 代价 |
| --- | --- |
| 断言「Docker 需要安装」而未先查 | 给了用户一个错误的待办项 |
| 首次容器内失败先怀疑依赖 | 绕了一圈才查到 shell 路径转换 |
| 写注释时混入英文词与一处缺空格 | 自己发现并修正，但属低级质量问题 |

反向验证了新增检查的有效性：临时删掉 `chem_invalid_structure` 文案行后，

### 一、纠正了决策登记表 A4 的一处错误记载

A4 原写「完全开源，商用免责」。核实结果：**这是README 里的功能描述，

两者必须区分。已向用户确认按「只做 HTTP 调用，不改 Fay 代码」实施——
GPL-3.0 的 copyleft 在**分发**时触发，纯 HTTP 调用不触发

### 二、契约靠读源码而非读文档确定

Fay 的飞书文档**需登录**才能访问；而 CSDN 等二手资料已出现与源码不符
之处（把 10002 说成 HTTP 接口）。故直接拉 `gui/flask_server.py` 核对。

**三个文档没记、但影响实现的事实**：

1. **业务失败仍返回 HTTP 200**——源码 `jsonify({'code':500})` 没传第二个
   参数。只看状态码的实现会把失败判成成功。已加测试锁定。
2. `user` 字段必须区分：非队列模式会清空该用户的前序音频队列，
   多学生共用 `"User"` 会互相打断。
3. **无认证**——故不携带凭据，且不建议把Fay 端口暴露到公网。

### 三、edge-tts 恰好绕开了本机的策略拦截

同为"被系统策略卡的第三方库"，edge-tts 反而能跑：
它是**纯 Python wheel**（`py3-none-any`，无原生扩展），
而 RDKit 的 `.pyd` 被拦导致本机完全不可用。

代价是它**调用微软在线服务**，断网必然失败——
故不得据此宣称"离线可用"，已登记为 B5。

### 四、三个被测试抓出的真实缺陷

都不让任何测试自然失败，且都不是"写错了"。

#### ① 配置从未被读到（最严重）

`settings or SpeechSettings()` ——后者用的是**默认值**而非环境变量，
于是 `XUEZHI_FAY_ENABLED=1` 完全没被读。**端到端打 `/health` 时才发现**
（报 `fay=未启用`）。

难以发现的原因：**默认值完全合法**→ 不报错；单元测试都注入配置 → 全绿。

> 这类"默认值合法 ⇒ 静默失效"与上轮修的 `DOMAIN_MESSAGES` 缺失同源。

#### ② 配置笔误让整个服务起不来

`XUEZHI_TTS_MAX_CHARS=-5` 会经`__post_init__` 抛 `ValueError`，
直接让 API 网关启动失败——与"语音可降级"定位矛盾。
纯空格音色 `"   "` 同理（真值故不走 `or` 分支）。

修复：`from_env` 内在读入处**夹取/回落**，不冒到构造器。

**教训**：配置来源不同，容错策略也应不同。
构造器收到 `-5` 该抛错（编程错误），环境变量读到 `-5` 该夹取（笔误）。
两者用同一个 `or` 表达式处理，必然有一边错。

#### ③ 本机 HTTP 代理劫持本地请求

Fay 在跑却报"返回错误"，细节是 **HTTP 502**——
`urllib` 默认读 `HTTP_PROXY`，把 `127.0.0.1:5000` 也丢给了代理。

**不能依赖部署环境恰好设了 `NO_PROXY`**（演示机环境不可控），
故显式用空 `ProxyHandler`。已设`HTTP_PROXY` 复测通过。

### 五、API 端点刻意不做

临时音频文件的生命周期是**真正的设计问题**（进程重启即失效、
多学生并发隔离、跨进程部署时临时目录不可共享）。
这些问题不解决就写端点，只会写出演示能用、部署即坏的接口。
已登记为待决策，不猜。

## F4：静态 OpenAPI 契约与漂移检测（2026-10-04 晚）

### 背景

F4 是登记表里「部分完成」的一项：OpenAPI 能实时生成，但
**未导出静态契约文件**，也**无契约变更检测**——
改字段不会导致任何测试失败。

### 一、为什么要静态契约

改接口字段却不更新契约，是**前端静默出错**的根源：
后端测试全绿（它测自己的实现），前端测试也全绿（它对着旧字段断言），
两边都对，只是**彼此不再匹配**。静态文件是双方共同的机器可读约定。

### 二、联网核实到的三个实践（未凭印象）

1. **必须 `python -m`**：直接执行脚本会把 `scripts/` 放到 `sys.path`
   最前，`from app.api.app` 失败。但 `-m` 又要求 `scripts` 是包——
   **两个问题一起解**：加 `scripts/__init__.py`。
2. **确定性三要素**：`sort_keys=True` + `indent=2` + 末尾换行。
   不排序则 diff 被格式抖动淹没。
3. **报错要说"哪里变了"**：契约上千行，逐行 diff 淹没关键信息。
   故报告新增/删除的端点与 schema，删除项加 `**` 标记。

### 三、写这个测试时自己犯的三个错

**① 断言基于错误假设**——`assert "sources" in required`。
查模型才发现 `sources` 用 `Field(default_factory=list)`，
**有默认值故契约里正确地不列为 required**。强制必填反而与实现不符。
> 真正的风险不是"必填与否"，而是**字段整体消失**（前端读到 undefined）。
> 改为校验：字段存在 + 类型是 array + 元素指向 SourceItem。

**② 按前缀盲抓导致两次误报**：先抓到 `tool_verified`
（`Verification` 枚举默认值，与错误码无关），
排除名单后又抓到 `tool_invocations`（`AnswerResponse` 的**字段名**）。
> **"长得像错误码的字符串"远多于错误码**，排除名单是打地鼠。
> 最终改为**结构化遍历 `enum` 数组**——不猜、不排除。

**③ 缩进期望值凭想象写的**：断言 2 空格，但第二层是 4 空格。
> **断言写出来也得实跑验证**。这已是本项目第三次同类教训。

### 四、一次工具事故

用 heredoc 追加文档时把 `EOF` 粘在了表格行尾，
导致命令文本被写进文档。**用文档格式测试没抓出来**
（它不检查这个），是我 `tail` 时肉眼发现的。
> 检查机制有盲区时，**主动查看输出尾部**是必要的补充。

### 五、反向验证

篡改契约（`/api/v1/molecule` 改名）后测试立即失败，并精准指出
「新增端点 / 删除端点」。确认检测有效且报错可用。

**测试：684 passed, 36 skipped**（契约测试 15 项）

## F5：可视化数据的机器可读 schema（2026-10-04 晚）

### 发现的缺口比预期严重

F5 登记的是「可视化数据 schema 版本待回填」。实测发现
**OpenAPI 根本覆盖不到 `viz_data`**——它在契约里是
`{"type": "object", "additionalProperties": true}`，
**对内部 12 个字段零约束**。

后果：后端删掉 `coords` 或改`atoms[].index` 语义时，
OpenAPI 契约检测**全绿**，前端却在运行时才炸。

### 关键判断：schema 放在后端而非前端

权威来源是 `engine.py`（它生产数据）。放在生产者旁边，
才能在**同一个提交**里同时改"产出什么"和"声明什么"——
否则两份定义必然漂移。前端 `types.ts` 是它的 TS 投影，由测试比对。

### 必须用真实校验器，不能手工查字段

手工写 `assert 'coords' in required` 只能验证"我想到的约束"，
**验证不了 schema 本身写得对不对**。
装了`jsonschema==4.26.0`（联网核实requires_python>=3.12兼容），
用 `Draft202012Validator` 做双向验证：
正确数据通过，7 类坏数据全部拒绝且**定位精准**（如`['atoms', 0, 'radius']`）。

### 三条 schema 检不出的风险（人工评审兜底）

机械检查完备会给人"检测完备"的错觉。这些是**语义漂移**：
1. `radius` 单位是 Å——改成 nm 则球体大小全错
2. `coords` 与 `render_atoms` 按索引一一对应——顺序不一致则原子会飘
3. `order` 为 1.5 表示芳香键——改成整数枚举则苯环画不出交替单双键

已登记为 `VIZ_SCHEMA_NOTES`，**与 schema 同处一个文件**。

### 又一次"断言自己撒谎"

断言 `assert "True" not in repr(schema)`，理由是「JSON 里应写 true」。
但 `additionalProperties: False` 里的 `False`
**本来就是合法 JSON Schema 关键字值**（"不允许额外字段"），
用 Python 的 `False` 才是正确写法。按字面搜会误报。

> 这是本项目**第四次**同类教训。断言写出来也得实跑验证——
> 无论它验证的是代码还是契约。

### 顺带锁定：芳香环离域表示正确

实测苯环 `order` 含 **1.5**。这与用户此前确认一致——
**离域是对的**，不应改成交替单双键。已加测试锁定。

**测试：717 passed, 36 skipped**（schema 测试 33 项，零回归）

## H21：语音 API 端点（2026-10-04 深夜）

用户决策：**两阶段交付**（JSON 返 audio_id + 独立音频端点），
**清理两条路径并存**（惰性 + 定时）。

### 差点照搬官方做法：BackgroundTask 不可靠

FastAPI 官方文档推荐用 `BackgroundTask` 在响应后删临时文件。
但联网核实 + 实测发现：

```text
starlette 1.7.0 的 BackgroundTask.__call__ 源码里无 CancelScope/shield
本项目正好用了 BaseHTTPMiddleware
```

### 三个实测抓出的缺陷

#### ① Dockerfile 漏 COPY scripts/

契约测试用 `python -m scripts.export_openapi`，
而镜像里根本没这个目录。报`No module named 'scripts'`
看起来像脚本路径写错，实则是 Dockerfile 疏漏。
**教训**：加了新的顶层目录，必须同步检查 Dockerfile 的 COPY。

#### ② 双向检查的采集范围漏了 speech 与 api

新增 `app/speech/errors.py` 后，采集器仍只扫
`llm/rag/chem/agent`——speech **完全不在检查范围内**，
双向检查对它**失效**。补上后立刻报出 5 个缺失码。

> **新加模块时要同步更新"检查的采集范围"**，
> 否则新模块天然处于无检查状态。

#### ③ classify 只查 API_ERROR_SPECS，状态码与文案矛盾

端到端实测：`HTTP 404` + `api_internal_error` + "服务内部错误"。
**自相矛盾**——学生看到 404 却被告知"服务内部错误"，
会以为重试有用，而重试同一 id 仍会 404。

根因：`own_code in API_ERROR_SPECS` 只覆盖 `api_` 前缀，
而 `speech_audio_gone` 在 `DOMAIN_CODE_SPECS`。已改为查两张表。

> 这类缺陷**结构上抓不到**：码登记了、文案也存在，
> 只是查找路径没走到。故按场景显式加断言。

### 一次自己的断言写错

断言 422 而实际 400。查证确认**项目一贯用 400**
（自定义校验处理器把 Pydantic 错误映射为 400 以替换英文文案）。
既有 test_app.py 全部断言 400。

> **跟随项目约定，而不是框架默认值。**

### 顺手改掉一个把架构决策写成断言的测试

`test_openapi_over_tcp` 原断言 `len(paths) == 5`——
把"当前有几个端点"这个架构事实写成了断言，
于是每加一个端点就得改测试（本次加语音端点时果然失败）。
改为断言**具体端点存在**：新增端点不必改测试，
端点被误删仍会失败。

**测试：742 passed, 36 skipped**（新增 23 项，零回归）
